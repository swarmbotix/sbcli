# `messages/` — message styles

Each subdirectory is a **style**: a self-contained namespace tree with its
own `message_definitions/` (source `.proto`) and, once compiled, its own
`message_targets/` (generated bindings).

| Style | Holds | Ships |
|---|---|---|
| `swarmbotix/` | `header/`, `primitives/`, `images/`, `sensors/` | the main style — swarmbotix's own definitions, FlatBuffers on the wire |
| `ros2/` | `std/` + the ROS2 mirror (`std_msgs`, `geometry_msgs`, `sensor_msgs`, …) | 138 `.proto` files |

Styles are an **open set** — drop `messages/<yourname>/message_definitions/`
in a user's `~/.swarmbotix/messages/` and it is usable immediately.

**There is no "active" style.** Every message is named in full,
`<style>/<namespace>/<Leaf>`:

```bash
sb message list                                    # every style
sb pub add -m ros2/std/StringStamped chatter --zenoh
sb pub add -m swarmbotix/images/Image480pMono8 cam --iox2
sb message compile --style ros2                    # a filter, not a mode
```

That is deliberate. One module routinely publishes one style and subscribes
to another, and `Header.metadata.msg_type` travels on the wire to consumers
that share no configuration with the publisher — so a name whose meaning
depends on the reader's config is not an identity.

Only `message_definitions/` is source-of-truth and version-controlled here.
`message_targets/` is generated by `sb message compile` and is disposable;
it is created per-style in the user's home, never in this repo.

## Cross-style imports are not supported

`protoc` runs with a single style's `message_definitions/` as its include
root, so a `.proto` in one style cannot `import` from another. The current
split is verified clean: nothing in the ROS2 namespaces imports `std/`, and
`std/` imports only `std/`.


## The `swarmbotix` style

| Namespace | Holds |
|---|---|
| `header/` | `Header` — UNIX timestamp in **nanoseconds**, `frame_id`, `seq`, and the `metadata` block L4 reads for per-topic rate. ns is the base unit so µs/ms/s are exact integer divides. |
| `primitives/` | `Vector3`, `Vector4`, `Quaternion`, `Mat33`, `Mat44`, `Pose`, `Twist`, `Transform` |
| `images/` | `Image` — **one** schema that fans out into 8 fixed-size iox2 types |
| `sensors/` | `Imu`, `LaserScan`, `PointCloud`, `GnssFix` |

### One image schema, many iox2 types

A variable-length payload has no single correct iceoryx2 size — an image is
230 KB at 360p mono8 and 6 MB at 1080p rgb8, and sizing one struct for the
worst case wastes shared memory on every small frame. So `images/Image.proto`
stays one file and the **build** fans out, driven by `iox2_variants` in
`sb.config.yml`:

| iox2 type | w × h × bytes/px | `data` capacity |
|---|---|---|
| `Image360pMono8` | 640 × 360 × 1 | 230,400 |
| `Image360pRgb8` | 640 × 360 × 3 | 691,200 |
| `Image480pMono8` | 640 × 480 × 1 | 307,200 |
| `Image480pRgb8` | 640 × 480 × 3 | 921,600 |
| `Image720pMono8` | 1280 × 720 × 1 | 921,600 |
| `Image720pRgb8` | 1280 × 720 × 3 | 2,764,800 |
| `Image1080pMono8` | 1920 × 1080 × 1 | 2,073,600 |
| `Image1080pRgb8` | 1920 × 1080 × 3 | 6,220,800 |

**The base `Image` type is not emitted for iox2.** It is precisely the type
with no correct size, so referencing it is always a mistake — the codegen
makes that impossible rather than documenting it. `Image` still exists
normally in the `proto/` and `fb/` outputs, where lengths are dynamic.

Add a resolution by adding an `iox2_variants` entry — never another `.proto`.

### Fixed-size repeated fields

`vec_caps` pins `repeated <scalar>` capacities per field, the same way
`bytes_caps` does for `bytes`. Without it every repeated field gets one
global number: `Mat33.data` would be a 256-element array holding 9 values,
and a lidar sweep would be truncated to 256 samples.

| Field | Elements |
|---|---|
| `swarmbotix.primitives.Mat33.data` | 9 |
| `swarmbotix.primitives.Mat44.data` | 16 |
| `swarmbotix.sensors.LaserScan.ranges` | 1080 |
| `swarmbotix.sensors.LaserScan.intensities` | 1080 |
