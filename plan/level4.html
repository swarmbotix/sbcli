L4 — Topic Introspection

After L4, with two L3 modules running, sb topic list shows their topics tagged [z] / [i], and sb topic listen <topic> streams decoded frames. Surface and output format mirror the swarmbotix_old/crates/sb-introspect prototype.

Scope

Commands

sb topic list   [-t <sec>] [-k <keyword>] [--case-sensitive]
                [--transport zenoh|iceoryx2|all] [--json]
sb topic listen <topic> [--transport zenoh|iceoryx2] [--raw] [-n <count>]
sb topic pub    <topic> '<bytes-hex>' [--transport zenoh|iceoryx2]
sb topic prune  [--json]

sb topic list

  • Zenoh: open short-lived session, declare ** wildcard subscriber, sleep window (default 500 ms), collect unique key expressions. First sample per topic wins — no rolling rate sampler.
  • iceoryx2: Service::list(Config::global_config(), …). Type name extracted from static_details.message_type_details().payload.type_name() — free from the registry, no subscribe needed.
  • Schema + rate decoding: any payload whose first few bytes parse as a protobuf std/Header populates schema from the descriptor (via L1 vault lookup) and rate_hz from header.metadata.msg_freq_desired. Foreign payloads stay null. Wireless wrapper, but L3 publishers always emit Header-leading *Stamped messages, so the columns fill in for sb-generated topics.
  • PID + liveness (iceoryx2 only): each iox2 service's dynamic_details.nodes records the UniqueNodeId of every Node that holds a publisher / subscriber port; UniqueNodeId::pid() gives the owning process. The discoverer picks the first alive node's PID and surfaces it; if every registered node maps to a process the OS reports as dead, the PID is still surfaced with is_dead = true so the renderer can append (dead) and operators can spot stale on-disk service registrations left by crashed publishers. Zenoh entries always render PID - — Zenoh doesn't put a publisher PID on the wire and we don't (yet) stamp it into Header.metadata.
  • Merge + sort alphabetically. Default table (the [z]/[i] tag is redundant with the /zenoh/ or /iox2/ segment in the path, but kept for at-a-glance scanning): 
      - [z] {rate:>6.1} Hz  {pid:<18}  {schema:<22}  {topic}
  - [i]      - Hz  PID 12345           std::StringStamped      /dev01/ws/cam/iox2/image
  - [i]      - Hz  PID 67890 (dead)    std/StringStamped       /dev01/ws/app1-1/iox2/hello
  - [z]   10.0 Hz  -                   std/StringStamped       /dev01/ws/talker/zenoh/chatter
  • --json emits one JSON line per TopicEntry instead of the table. Field set is pinned (snapshot-tested in level4_output_format): topic, transport, schema, hash, rate_hz, publisher_pid, is_dead.

sb topic listen <topic>

  • Bare chatter resolves to /<device>/<workspace>/<module>/<transport>/chatter via cwd's sb.dev.yml when there's exactly one matching subscriber/publisher (the transport segment comes from that entry's --iox2/--zenoh). Ambiguous or no-match → error. Fully-qualified path is passed through unchanged.
  • Default Zenoh: receive raw bytes; attempt protobuf decode against the schema in the cwd module's sb.dev.yml; emit JSON line per frame.
  • Default iceoryx2: subscribe via the Service::list-discovered type when it's one of the bundled std/* messages; otherwise error telling the user to pass --raw.
  • Output (one JSON line per frame): {transport, topic, schema, hash, encoding, payload} — identical envelope shape to the prototype's. Fields stay null when L4 can't infer them honestly.
  • --raw: skip decode, payload is {kind: "hex", bytes: "deadbeef…"}.
  • -n N: stop after N frames; 0 (default) runs until SIGINT.

sb topic pub <topic> '<bytes-hex>'

  • Publishes raw bytes via the resolved transport. One-shot.
  • JSON-via-schema variant (sb topic pub /chatter '{"data": "hi"}') — encode through vault, publish — added once a clean error message exists for foreign / un-decodable schemas. Stretch goal for L4; otherwise L5.

sb topic prune

  • Cleans the stale on-disk registrations sb topic list flags with (dead). Walks Node::<ipc::Service>::list(Config::global_config(), …), and for every NodeState::Dead(view) calls view.try_remove_stale_resources(). iceoryx2-only — Zenoh has no on-disk state to prune.
  • iceoryx2's ResourcesAlreadyCleanedUp is treated as success — another instance got there first; the net state is what the caller asked for.
  • Default output: a Pruned N dead iceoryx2 node(s): block listing the cleaned PIDs, plus one warning: failed to prune PID <n>: <reason> per failure on stderr. Nothing stale → No dead iceoryx2 nodes found. Non-zero exit iff any node failed to clean.
  • --json emits one PruneReport JSON object: {cleaned_pids: [u32], failed: [[pid, reason], …]}.

TDD plan

1. Live discovery — Zenoh
Integration harness spawns a Zenoh publisher in a thread on a known key. sb topic list finds it within the sleep window. Tagged [z]. tests/integration/level4/discover_zenoh.rs.
2. Live discovery — iceoryx2
Same shape using Service::list. Tagged [i]. Schema column populated from type_name(). #[ignore]'d if shmem unavailable in CI (per feedback_topic_discovery).
3. End-to-end against L3 publishers
Scaffold a Rust module (L2), sb pub add -m std/StringStamped /hello --zenoh (L3), spawn the module, then sb topic list shows the topic with schema std/StringStamped and rate matching the publisher's declared msg_freq_desired. This is the integration test the new ordering exists to enable.
4. Keyword filter — ported from prototype
Port the matches_keyword tests from swarmbotix_old/crates/sb-introspect/src/discover.rs verbatim: case-insensitive by default, --case-sensitive flips it, empty keyword matches everything. Drift between prototype and rewrite is the bug this catches.
5. Output-format snapshot — table + JSON
Given a fixed Vec<TopicEntry> (mix of [z] / [i] rows, some with schema, some with rate, some with neither), assert byte-identical table output AND --json output against checked-in fixtures via insta. This contract is what lets later levels enrich without breaking the CLI surface.
6. Bare-topic resolution
chatter → fully-qualified when cwd's sb.dev.yml has exactly one publisher/subscriber of that name. Ambiguous → error lists candidates. No sb.dev.yml in cwd → require fully-qualified. Fully-qualified path passes through unchanged.
7. listen decode against L3 publisher
Run an L3-scaffolded Rust publisher of std/StringStamped; sb topic listen /hello emits a JSON line with schema: "std/StringStamped" and decoded payload. --raw on the same topic emits hex.
8. pub round-trip
Spawn subscriber in thread; CLI sb topic pub /hello deadbeef → subscriber sees the exact 4 bytes. One test per transport.
9. Rate from single sample
L3-scaffolded publisher writes msg_freq_desired: 10.0 in its Header. sb topic list -t 0.2 (short window — could miss multiple samples) still reports 10.0 Hz. Verifies the L1 design payoff: rate comes from the Header field, not sample counting.

Why this is L4

  • L4 finally gets to test discovery against real sb-generated publishers (from L3) instead of throwaway Zenoh examples. The integration tests mean something now.
  • L1's Header.metadata.msg_freq_desired design becomes useful here — any L3 *Stamped publisher fills the rate column for L4 from one sample.
  • Topic introspection is the highest-leverage user-visible feature after pub/sub itself ("the ros2 topic echo ergonomics" from the requirements). Putting it here also means it ships before launch/orchestration (L5), so dev-loop visibility is in place before sb up exists.
