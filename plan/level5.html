L5 — Launch & Production

After L5 the user can launch every module in the active workspace in one shot with sb up, attach/kill the session, and freeze any module for production with sb gopro. This is where the multi-module workspaces created at L2 actually start running together.

Scope

Launch (tmux/psmux)

sb up                              # launch all modules in active workspace
sb run <module> [args...]          # launch a single module; args -> runscript.bash
sb stop <module> [args...]         # stop a single module via its stopscript.bash
sb down                            # kill the session
sb attach                          # attach to it
  • Session name: sb-<workspace>. One pane per (module, instance) pair — a module without an instances: entry in flow.yaml gets one un-suffixed pane (current behavior); a module with N declared instances gets N panes named <module>-<id> (matching the runscript's tmux session-name suffix).
  • Each pane: cd <module.root> && ./runscript.bash [args...]. sb up passes no args; sb run <module> [args...] forwards trailing args verbatim — the --id <id> convention for instanced modules is one such use, but any args the runscript accepts are fair game.
  • sb stop <module> [args...] is the symmetric counterpart: same module resolution, same sb-<workspace> session, same respawn-window -k idempotency, but swaps stopscript.bash in for runscript.bash. Errors clearly if no stopscript is present (no sb init stub today — user authors it alongside the runscript).
  • Module root + script path resolved via the active workspace's flow.yaml (from L2) → each module's sb.dev.yml. Instance fan-out resolved via flow.yaml::instances (also from L2 — see L2).
  • Windows: psmux ships as the tmux command — no platform-specific code in sb.

L2 already lands the data model and the docker-flavored runscript. L5's job is to walk flow.modules × flow.instances at launch time and spawn the right pane per pair; sb-launch's current single-pane-per-module loop predates this and will fan out as part of L5.

Production export

sb gopro                  # one module: dev.yml + io_dir → prd.yml
sb gopro --all            # every module in active workspace
  • Reads sb.dev.yml + walks io_dir/ to confirm files exist; emits sb.prd.yml.
  • Strips: root:, absolute paths, anything host-specific.
  • Keeps: module name, full publishers + subscribers list with types & transports.
  • Resulting sb.prd.yml is language-agnostic and ships with the binary — L6 swarmctl reads it for the design-time view.

TDD plan

1. sb up launches expected panes
2-module workspace → sb up → tmux list-windows -t sb-<ws> reports 2 panes. Each pane's working dir matches the module root. Cleanup with sb down: tmux has-session returns non-zero.
2. sb up handles missing runscript
Module with no runscript.bash → sb up exits non-zero before creating the session (no orphan tmux). Message names the offending module.
3. sb up handles no active workspace
With ~/.swarmbotix/active empty/missing: sb up errors immediately with an actionable message (suggesting sb ws set). No tmux session created.
4. sb run <module> is idempotent
Launches exactly one pane in sb-<ws>. Re-running with the same module name kills + restarts the existing pane, doesn't duplicate.
4a. sb run <module> [args...] forwards args to runscript.bash
Trailing args after <module> reach the runscript's $@ unmodified, including args that start with - and args containing spaces. sb stop <module> [args...] mirrors this for stopscript.bash; both verbs share the sb-<workspace> session and the same idempotent respawn semantics.
4b. sb stop blames a missing stopscript
Module with a runscript but no stopscript.bash → sb stop <module> errors before touching tmux. Message names the module and the missing filename so the user knows what to author. Unknown module name on either verb fails the same way (TDD #4).
5. sb attach / sb down round-trip
After sb up: sb attach in non-interactive mode reports the session name and exits 0 (or attaches in an interactive shell). sb down tears the session down; subsequent sb attach errors with "no session".
6. sb gopro output is sanitized
After gopro, sb.prd.yml contains no /home/ / /Users/ / C:\ substrings, no root: key. Lints fail loudly if any leak.
7. sb gopro round-trip
Non-trivial sb.dev.yml (3 pubs, 2 subs, mixed transports) → gopro → parse sb.prd.yml → publishers + subscribers identical to dev (ignoring host fields). Sanity check that gopro doesn't drop entries.
8. sb gopro --all covers every module
3-module workspace → sb gopro --all → each module's root contains a fresh sb.prd.yml that round-trips. Modules without an io_dir/ on disk surface as a clear per-module error without blocking the others.
9. Full end-to-end smoke
Script (CI step, not unit): 
sb ws create demo && sb ws set demo                                # L2
cargo new pubber && sb init --rust ./pubber                        # L2 (user creates Rust crate; sb adopts it)
echo 'cargo run' > pubber/runscript.bash                           # L2 (fill in the runscript stub)
sb pub add -m std/StringStamped /hello --zenoh --module pubber     # L3
cargo new subber && sb init --rust ./subber                        # L2
echo 'cargo run' > subber/runscript.bash                           # L2
sb sub add -m std/StringStamped /hello --zenoh --module subber     # L3
sb up                                                              # L5
sleep 3
sb topic list                                                      # L4 — finds /hello tagged [z]
sb topic listen /hello -n 1                                        # L4 — one frame, schema decoded
sb down                                                            # L5
sb gopro --all                                                     # L5 — both modules get sb.prd.yml
This is the proof-of-life for the whole stack from L1 through L5.

Why this is L5

  • Launch needs flow.yaml (the multi-module registry, from L2) and module-level runscript.bash (from L2) and the per-module pubs/subs that make running together meaningful (from L3). Both prerequisites are in place by the time L5 starts.
  • gopro is a pure transform on sb.dev.yml + io_dir/ — small, but it ties off the dev → prod boundary cleanly before swarmctl reads sb.prd.yml at L6.
  • L4's topic introspection slotted in before this on purpose: sb topic list/listen is more leveraged for daily dev work than orchestration is, so it ships earlier.
