L3 — Pub/Sub Management & Codegen

After L3, inside a module directory (one the user adopted via sb init at L2) the user runs sb pub add -m std/StringStamped /hello --zenoh and a working publisher file appears under swarmbotix_io/publishers/. Two such modules can now exchange messages over a real transport. Five languages × two transports.

Largest level. Recommend splitting per-language into separate PRs after the config-mutation half lands. Rust first (dogfood), then Python, C++, Flutter, Unity.

Scope

Config mutation — --module is optional

sb list           [--module <name>]                                   # all pubs + subs
sb pub list       [--module <name>]
sb pub add        -m <MsgType> <topic> [-n <name>] [--iceoryx | --zenoh] [--module <name>]
sb pub edit <name>  [-m <MsgType>] [-t <topic>] [--module <name>]
sb pub rm   <name>  [--module <name>]
sb sub list       [--module <name>]
sb sub add        -m <MsgType> <topic> [--iceoryx | --zenoh] [--module <name>]
sb sub edit <topic> [--module <name>]
sb sub rm   <topic> [--module <name>]

-m is reserved for MsgType — module uses the long-only flag --module <name> to avoid the clash.

Module resolution at L3

  1. No --module flag → operate on ./sb.dev.yml in cwd. Error if absent.
  2. --module <name> given: try, in order, (a) ./<name>/sb.dev.yml as a direct child of cwd, then (b) the active workspace's flow.yaml (from L2). The first hit wins; error with the paths searched if both miss.

The direct-child lookup is useful when the user is in a parent directory holding several module dirs side-by-side; the flow.yaml lookup makes the named form work from anywhere on disk once a workspace is active. Both layers are available at L3 because L2 ships workspaces.

  • Validates: MsgType exists in L1's vault; topic not duplicate; transport explicit, else defaulted from L1's sb.config.yml (transport_on_device / transport_cross_device).
  • edit is a diff, not a replace — preserves field ordering and comments.
  • After every mutation: codegen runs and emits/updates/removes the language file under <io_dir>/publishers/ or subscribers/.

Codegen — per-language templates

Engine: minijinja (templates live in crates/sb-codegen/templates/). Every template emits raw transport API calls against the protobuf-generated types from L1's vault — no Swarmbotix wrapper.

TDD plan

1. pub add golden file on sb.dev.yml
Empty sb.dev.yml → sb pub add -m std/ImageStamped /image_raw --iceoryx → produced file matches checked-in golden byte-for-byte. Repeat for sub add, pub edit, pub rm.
2. Validation errors
sb pub add -m Nonexistent /foo → exits non-zero, message contains "Nonexistent" + "not in vault" + suggestion to run sb message list. sb pub add -m std/String /existing-topic → exits non-zero, "topic already used by <publisher_name>".
3. Module resolution — cwd, sibling, and workspace
Tempdir layout: parent/{pubber,subber}/sb.dev.yml. From parent/: sb pub list --module pubber reads pubber/sb.dev.yml; bare sb pub list errors ("no sb.dev.yml in cwd"). From parent/pubber/: sb pub list works on cwd; sb pub list --module subber finds the sibling. Then with an active workspace registering pubber at an absolute path: from an unrelated cwd (/tmp), sb pub list --module pubber resolves via flow.yaml. Naming a non-existent module errors with all paths searched.
4. Transport defaulting
With no --iceoryx/--zenoh flag, defaults from sb.config.yml (transport_on_device: iceoryx2 → iceoryx2). $SB_CONFIG override flips it. Explicit flag always wins.
4. Codegen snapshot — per (language, transport)
10 snapshot fixtures (5 languages × 2 transports, minus Flutter/Unity iceoryx). Each: known sb.dev.yml snippet → generated file matches golden. Run via insta for easy review.
5. Generated Rust file compiles inside a real Rust crate
Test fixture: a minimal Rust crate with zenoh = "1.9" + iceoryx2 = "0.9" in Cargo.toml, adopted via sb init --rust. Run sb pub add -m std/StringStamped /hello --zenoh, then cargo check succeeds. Catches API drift in the pinned transport versions. (sb does not add the deps for the user — the fixture provides them, mirroring real usage where the user maintains their own Cargo.toml.)
6. Generated Python file imports inside a real Python project
Test fixture: a Python project with eclipse-zenoh installed in the env, adopted via sb init --python. Run sb sub add -m std/StringStamped /hello --zenoh, then python -c "import swarmbotix.subscribers.hello" succeeds. (As above, the test env provides the dependency.)
7. Mutation triggers file emit/update/rm
After sb pub add, the file exists under swarmbotix_io/publishers/. After sb pub rm, it's gone. After sb pub edit -t /new_topic, the file's key expression / service name updates.
8. sb list rendering
Golden file. sb pub list filters to publishers only; columns: name / type / topic / transport.
9. End-to-end Rust ↔ Python over Zenoh
Two fixture projects (a Rust crate + a Python project) adopted via sb init: pubber (Rust) publishes std/StringStamped on /hello; subber (Python) subscribes. Spawn both, publish from Rust, assert Python subscriber's stdout contains the expected payload. tests/integration/level3/cross_lang_zenoh.rs.
10. End-to-end Rust ↔ Rust over iceoryx2
Two fixture Rust crates adopted via sb init --rust exchanging std/ImageStamped via iceoryx2. Verifies zero-copy path. #[ignore]'d if shmem unavailable in CI.

Why this is L3

  • Needs the vault (L1) for MsgType validation and for codegen to template against the right field set.
  • Needs L2-adopted modules (with sb.dev.yml + swarmbotix_io/ in place) so codegen has somewhere to drop generated files — and so integration tests can target realistic user projects, not handmade fixtures.
  • Pays off L1's Header.metadata.msg_freq_desired design: any *Stamped publisher generated at L3 writes its declared Hz into each frame, which L4's topic-list then reads from a single sample.
