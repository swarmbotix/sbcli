L2 — Workspaces & Module Init

After L2, the user creates a workspace, sets it active, points sb init at an existing project directory (Rust crate, Python project, C++ tree, Flutter project, Unity project), and sb drops in its bookkeeping files (sb.dev.yml, a runscript.bash stub, an empty swarmbotix_io/) plus registers the module in flow.yaml. sb does not create the user's project — only adopts it.

Scope

Workspaces — directories at ~/.swarmbotix/workspaces/<name>/

sb ws create <name>     # mkdir ~/.swarmbotix/workspaces/<name>, init empty flow.yaml
sb ws set    <name>     # write <name> to ~/.swarmbotix/active
sb ws list              # list dirs under ~/.swarmbotix/workspaces/, mark active with *
sb ws delete <name>     # rm -rf; clear active if it was set
  • Backed by L1's WorkspaceFlow type (already defined for flow.yaml R/W).
  • ~/.swarmbotix/active is a one-line file holding the active workspace name. Missing or empty = no active workspace; not an error on its own.
  • sb ws delete clears active if the deleted workspace was active, with a stderr warning.

Module init — sb init

sb init [<rootpath>] [--rust | --python | --cpp | --flutter | --unity] [--docker] [--force]
  • <rootpath> defaults to . (cwd). For Unity, point at the project root that contains Assets/.
  • Module name = basename(rootpath). Must be a valid identifier (no spaces/slashes; same rule as workspace names).
  • Active workspace required — without one sb init errors with an actionable message (suggesting sb ws create / sb ws set).
  • Language flag: required if no sb.dev.yml exists at <rootpath> yet (sb needs to know what to write); optional if one exists (must match the existing language: tag if given, else error).
  • Idempotent: re-running sb init on an already-adopted dir is a no-op (no duplicate entry in flow.yaml, no clobbered files).

What sb writes into <rootpath>

Each file is written only if missing (unless --force). sb never touches the user's existing project files.

  • sb.dev.yml — module: <basename>, language: <lang>, io_dir: swarmbotix_io/ (or Assets/Scripts/swarmbotix_io/ for Unity), empty publishers: / subscribers: lists.
  • runscript.bash — executable stub. The body prints a TODO message and exits non-zero. The header is a comment block describing the contract (working dir = module root; this is what sb run/sb up invokes) and example commands per language so a human or LLM agent can fill it in: 
    #!/usr/bin/env bash
# runscript.bash — invoked by `sb run` / `sb up`. Working dir = this module's root.
# Fill in the command(s) that build and start this module. Examples by language:
#   Rust:     cargo run --release
#   Python:   python main.py
#   C++:      cmake --build build && ./build/app
#   Flutter:  flutter run -d linux
#   Unity:    : nothing — Unity runs from the editor
#
# Tip: point your LLM agent at this file plus your project tree.

echo "TODO: configure $(pwd)/runscript.bash" >&2
exit 1
  • swarmbotix_io/ directory (or Assets/Scripts/swarmbotix_io/ for Unity) — empty; L3 codegen fills it.

Flow.yaml registration

After writing the files, sb init appends <module> → /abs/path/<rootpath>/sb.dev.yml to ~/.swarmbotix/workspaces/<active>/flow.yaml under the modules: map. Already-present entries are left untouched (idempotency).

flow.yaml::instances — per-module deployment topology

WorkspaceFlow now carries an optional instances: block per module. Each entry is a ModuleInstance { id, label?, docker?, args? }. Instances are the unit of node identity in the L6 graph editor; they also drive docker-aware runscript codegen at L2. A module without an entry runs as a single un-suffixed process (the default; matches the pre-instances flow.yaml shape, which still parses unchanged).

No management subcommand at L2 — users hand-edit flow.yaml and re-run sb init --docker --force. WorkspaceFlow::validate() rejects invalid instance ids (empty / spaces / slashes / dots) and duplicate ids within a single module's list, called from read_flow so bad input fails at load time. ID character class matches topic.rs::is_valid_segment_char ([A-Za-z0-9_-]+) — wider than validate_identifier because - must be allowed for IDs like front-left.

Docker-flavored runscript — sb init --docker

With --docker, sb emits a runscript whose body dispatches on --id <name> to one pre-resolved docker run invocation per instance declared in flow.yaml::instances.<module>. Image, env, devices, mounts, gpus, and network flags are baked in at sb init time — the runscript performs no flow.yaml lookup at runtime and has no dependency on sb being on PATH.

  • Preflight: active workspace required; flow.yaml::instances.<module> must exist and be non-empty; every instance must have docker.image. Each failure prints an actionable error and exits non-zero; runscript.bash is not written.
  • Staleness check: embedded in the runscript header; compares mtime of flow.yaml vs the runscript itself. If flow.yaml is newer, emits one stderr warning and continues. Regenerate with sb init --docker --force.
  • Container identity: docker run --name <module>-<id> --hostname <module>-<id>. The hostname matches so in-container code that derives identity from hostname (logging, ROS adapters) picks up the instance label without re-parsing argv.
  • Argument threading: "$@" follows the image, so the in-container main() still sees --id <name> and uses it to rewrite its wire topic segment (see documents/sbcli_pubsub_consuming.md §3 — string-form ids are interchangeable with the original numeric form).
  • Contract doc: documents/sbcli_docker_runscript.md — schema reference, per-language in-container entry-point sketches, pitfalls. Treat this as the docker counterpart of the pub/sub consuming doc.

Out of scope at L2

  • Project creation. sb does not run cargo new, flutter create, or any equivalent. Users bring their own project — sb only adopts it.
  • Pubs/subs. No publishers or subscribers yet. The user runs sb init, then at L3 adds sb pub add ....
  • Codegen. L2 doesn't touch swarmbotix_io/ beyond creating an empty directory. L3 owns codegen.
  • Launch / tmux. No sb up/down/run/attach yet — L5 owns multi-module orchestration. The runscript stub is in place but users invoke it manually until L5.
  • Production export. sb gopro lands at L5.

TDD plan

1. Workspace lifecycle round-trip
Tempdir $HOME: create ws1 → list shows ws1 → set ws1 → active marker = ws1 → create ws2 → set ws2 → delete ws2 → active cleared with warning → delete ws1. Each step inspects the filesystem directly.
2. sb init no active workspace
Tempdir project + no ~/.swarmbotix/active → sb init --rust . exits non-zero with a message naming sb ws set. No files written into the project, no flow.yaml mutation.
3. sb init on an empty dir writes the three artifacts
Tempdir empty, active workspace = demo: sb init --rust ./pubber writes pubber/sb.dev.yml, pubber/runscript.bash (executable bit set), pubber/swarmbotix_io/ (empty). Appends pubber → /abs/.../pubber/sb.dev.yml to ~/.swarmbotix/workspaces/demo/flow.yaml. Direct filesystem assertions.
4. sb init is idempotent
Run sb init --rust ./pubber twice. Second call exits 0, doesn't touch any file's mtime, doesn't duplicate the flow.yaml entry. Then run a third time without --rust: also exits 0 (no-op; language tag already on disk).
5. sb init preserves user files
Tempdir containing a real Rust crate (Cargo.toml + src/main.rs with arbitrary code): sb init --rust . → cargo check still passes; Cargo.toml + src/ bytes unchanged; the three sb artifacts now exist alongside. Repeat for Python (don't touch pyproject.toml / main.py), C++ (don't touch CMakeLists.txt), Flutter (don't touch pubspec.yaml), Unity (don't touch Assets/ contents).
6. Language flag handling
(a) No sb.dev.yml + no language flag → exits non-zero, message names the required flags. (b) Existing sb.dev.yml: language: rust + sb init --python → exits non-zero, "language tag mismatch". (c) Existing sb.dev.yml: language: rust + sb init (no flag) → succeeds (just registers, no language to choose).
7. sb.dev.yml shape
For each language: sb init --<lang> ./demo produces a sb.dev.yml that parses into ModuleDevConfig with the right module, language, io_dir (swarmbotix_io/ for the four; Assets/Scripts/swarmbotix_io/ for Unity), empty pub/sub lists. Direct serde assertion, no shell-out.
8. runscript.bash stub contents
Each language produces a runscript.bash whose body exits non-zero (TODO behavior) and whose header comment contains the per-language example line (golden snippet test on the comment block). Executable bit set; shebang is #!/usr/bin/env bash.
9. Unity io_dir
Tempdir with Assets/Scripts/ already present: sb init --unity . writes sb.dev.yml at the rootpath (next to Assets/) with io_dir: Assets/Scripts/swarmbotix_io/, creates the Assets/Scripts/swarmbotix_io/ dir, leaves all other Assets/ contents untouched.
10. Refuse-to-overwrite
With sb.dev.yml already at <rootpath> from a manual edit: bare sb init only registers (doesn't rewrite). sb init --force --rust . wipes and rewrites both sb.dev.yml and runscript.bash. A test fixture mid-edit verifies the no-force path preserves user comments / formatting.
11. Module name validation
Reject rootpaths whose basename isn't a valid identifier (demo-app, 123demo, empty, names containing spaces or slashes). Workspace names follow the same rule. One table test.
12. flow.yaml::instances schema
Unit-level (in sb-core/src/config.rs): WorkspaceFlow with a populated instances: block round-trips through serde_yaml unchanged; pre-instances flow.yaml (modules only, no instances: key) still parses (backwards compat); flow.instance("cam", "left") resolves; WorkspaceFlow::validate() rejects empty / whitespace / / / . ids and duplicate ids within a single module's list.
13. sb init --docker emits a docker-flavored runscript
Sandbox + pre-seeded flow.yaml::instances.cam_gige_ht with left + right: sb init --cpp --docker ./cam_gige_ht writes a runscript.bash that contains 'left') and 'right') case branches, --name 'cam_gige_ht-left' / 'cam_gige_ht-right', the env / device / gpu flags from flow.yaml, the image then "$@", the "known: left right" error hint, and the staleness-check preamble. Executable bit set.
14. sb init --docker preflights
(a) No instances: entry for the module → exits non-zero, stderr names flow.yaml and sbcli_docker_runscript.md; runscript.bash not written. (b) Instance without docker: → same shape, error names the offending instance id. (c) Instance with docker: but no image: → same shape, error names the offending instance id and the missing field.
15. sb init --docker --force regenerates from updated flow.yaml
First run produces a runscript with left + right branches. Rewrite flow.yaml to drop right and bump the image tag. Bare sb init --cpp --docker (no force) leaves the runscript unchanged. sb init --cpp --docker --force regenerates: only left branch remains; new image appears.
16. Generated docker runscript behavior
Three end-to-end shell asserts (no docker daemon required — every path exits before invoking docker run): missing --id exits 2 with --id <name> required and the known list; unknown --id ghost exits 2 naming the unknown id and the known list; touching flow.yaml after init produces a one-line staleness warning on stderr when the runscript is next invoked (the warning fires before id dispatch, so an unknown id still surfaces it).

Why this is L2

  • L3 (pub/sub management) operates on a module's sb.dev.yml, and its --module <name> flag wants to find modules by name. Both need modules to exist and a workspace registry to look them up in — settling that here keeps L3 focused on codegen.
  • "Adopt-don't-create" is a deliberate scope cut. Generating language-specific project skeletons (Cargo.toml, pyproject.toml, CMakeLists.txt, …) is a maintenance burden — every Rust edition bump, every flutter SDK change, every C++ toolchain quirk would land here. By treating sb as swarmbotix's bookkeeping rather than a project generator, L2 stays tiny and language-agnostic.
  • Workspaces are conceptually inseparable from modules — you almost never want one without the other. Folding workspace lifecycle and module init into the same level removes the cross-level dependency that existed when workspaces were at L5.
  • L2 is independently useful: a user can sb ws create demo && sb ws set demo && sb init --rust ./my_existing_crate, fill in runscript.bash, run it manually, and ignore the rest of sb. The forge is opt-in.
