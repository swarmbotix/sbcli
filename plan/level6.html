L6 — swarmctl REST + MCP + Web UI

Three surfaces, one core. Every REST and MCP endpoint maps to a CLI verb already shipped in L1–L5. The Web UI never has logic the CLI lacks.

Scope

swarmctl server

  • Started by sb ui (tmux pane on demand — no daemon).
  • Two HTTP surfaces on the same port:
    • REST at /api/* — thin wrapper, one route per CLI verb.
    • MCP at /mcp — same operations, MCP transport for AI agents (Cursor, Claude Code, etc.).
  • Both delegate to the same crates the CLI uses (sb-core, sb-vault, sb-pubsub, sb-codegen, sb-discover, sb-workspace, sb-launch, sb-gopro). No business logic in the server layer.

Web UI — design-time view

  • Reads flow.yaml, then each module's sb.dev.yml (or sb.prd.yml if present).
  • Node identity = (module, instance) pair. A module with N declared flow.yaml::instances (see L2) draws as N separate boxes labelled instance.label ?? instance.id; a module without an instances: entry draws as one un-suffixed box (backwards compat with the pre-instances flow.yaml shape).
  • Each box's wire-segment for edge derivation is <module>-<id> when instanced, <module> when not — matching the runtime topic path produced by TopicOverrides (see documents/sbcli_pubsub_consuming.md §3).
  • Draws publishers on the right (output ports), subscribers on the left (input ports).
  • Derives edges by matching topic names. No manual edge declaration.
  • Right-click on a module box → add/remove publisher or subscriber. Calls REST → same effect as the L3 CLI. Note: publisher/subscriber edits target the module, not the instance — instance IDs are launch-time only and never appear in sb pub add's flag surface (see documents/sbcli_docker_runscript.md §7).

Web UI — runtime view

  • Overlays live discovery (uses L4's sb-discover crate, called via REST).
  • Coloring is per-instance node: cam_gige_ht-left can be green while cam_gige_ht-right is orange — they are independent nodes with independent wire paths.
  • State per port:
    • Green: designed and live.
    • Orange: designed but not live (mismatch — app may be down, or topic name diverged).
    • Gray (unknown): live but not in design (unregistered publisher, stale leftover, or — common with instances — a publisher running with an --id that isn't declared in flow.yaml::instances).

TDD plan

1. REST contract test per route
For every CLI verb that has a REST counterpart, two tests: (a) hitting the route mutates filesystem state identically to running the CLI; (b) GET routes return JSON matching a checked-in schema. Use tower::ServiceExt for in-process HTTP testing — no live server needed.
2. MCP endpoint parity
Enumerate the union of L1–L5 operations; assert each appears in the MCP tool list with a JSON schema. tools/call on each verb produces the same effect as the matching REST call.
3. Design-time edge derivation
Fixture flow.yaml with 3 modules; one publishes /foo, another subscribes to /foo; GET /api/graph/design returns one edge. Add a third module that also subscribes to /foo → two edges from the same source.
4. Runtime overlay state machine
Stub sb-discover with controllable input. For each combination (designed × live, designed × not-live, not-designed × live), assert the returned port state is green / orange / gray respectively. No flakiness from real Zenoh in this test.
5. Live overlay smoke
2-module hello-world from L5; spawn it via sb up; GET /api/graph/runtime returns both ports green. Kill the publisher; within 3s the publisher port flips to gray (was live, now gone) and the subscriber port to orange (designed, not live).
6. UI ↔ CLI observational equivalence
Click "add publisher" in a headless browser (Playwright); assert resulting sb.dev.yml diff matches running sb pub add with the same args. One end-to-end test per UI mutation; saves manual QA.
7. sb ui launch
sb ui starts the server in a tmux pane, waits for /api/health to return 200, then opens browser (mocked in test). sb ui a second time is a no-op (reuses existing pane).

Why this is L6 (last)

  • Built on top of every other crate. The server must never have logic the CLI lacks; building it last guarantees the CLI surface is complete first.
  • Runtime view depends on L4's discovery + L5's launch — every dependency is shipped.
  • Web UI tooling (build pipeline, browser tests) adds enough surface that landing it earlier would slow L1–L5 reviews.
